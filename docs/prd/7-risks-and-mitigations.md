# 7. 위험 및 대응

- 임베딩 성능/품질 미확실성 → 작은 코퍼스로 MVP 검증, 프로바이더 플러거블 설계
- 파일 시스템 접근 제약(샌드박싱/권한) → macOS 권한 안내/요청 UX 설계, 접근 실패시 폴백
- 프로세스 관리(백엔드) → 실패 시 재기동/로그 확보, 개발/배포 모드 분리
- 대용량 인덱싱 시간/자원 → 증분 인덱싱/쿼터/스케줄러(후속)

## 7.1 Breaking Change Risks
- API 호환성: Backward compatible 우선. 계약 변경은 새 버전/필드 추가 방식으로 처리하고, 기존 필드는 유지·Deprecated 주기를 문서화한다.
- DB 마이그레이션: Expand–Migrate–Contract 3단계 전략 우선(추가 → 데이터 이동 → 구 필드 제거는 후속 릴리스에서 수행).
- 단축키 충돌: 시스템/앱 단축키 충돌 매트릭스를 확인하고, 충돌 시 대체 조합을 제시한다.
- 성능 퇴화: 인덱싱/검색 SLA(p50/p95)를 관찰하고, 퇴화 시 기능 플래그로 단계적 비활성화를 검토한다.

## 기존 기능 보존 원칙(호환성)
- 변경은 가능하면 추가적(additive) 방식으로 수행하고, 기존 라우트/스키마의 파괴적 변경을 지양한다
- 새 기능은 feature flag로 가드하며, 장애 시 우아한 폴백으로 기존 파일 탐색 흐름에 영향이 없도록 한다
- Dock 단축키는 시스템/앱 기본 단축키와 충돌하지 않도록 최종 확정 후 문서화한다
- 백엔드 비가용 시 클라이언트는 오류 상태를 사용자 친화적으로 노출하고 기존 UI 흐름은 지속한다
