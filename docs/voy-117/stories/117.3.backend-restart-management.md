# Story 117.3: Backend 재기동 관리 강화

## Status
Done

## Story
**As a** 사용자,  
**I want** backend가 중단되더라도 Helper가 복구하길,  
**so that** Voyager 기능이 지속적으로 동작한다.

## Acceptance Criteria
1. Helper는 backend 종료를 감지하고 backoff 정책에 따라 재기동을 시도한다.
2. Helper 종료 경로에서는 backend 프로세스를 항상 정상 종료하도록 보장한다. (앱 종료/수동 종료/비정상 종료에서 가능한 범위)
3. 최대 재시도 초과 시 Helper는 즉시 종료된다.
4. source/bundled 모드 모두 동일한 재기동 정책이 적용된다.
5. 기존 실행 경로(uv run, bundled binary)는 유지된다.
6. backoff는 1s → 2s → 4s → 8s → 16s(최대 5회 재시도)로 적용한다.
7. 최대 재시도 초과 시 로그를 남기고 UI 알림 없이 종료된다.
8. 변경 전후 회귀 동작이 수동 QA로 확인된다.
9. backend 시작 실패(프로세스 실행 실패, 기동 후 2초 이내 종료, 포트 검증 실패)에도 재시도 카운트가 증가하고 동일한 backoff 정책이 적용된다.
10. Helper의 의도적 종료(앱 종료/수동 종료) 시 재기동 루프가 실행되지 않는다.
11. backend 시작 실패 기준은 `Process.run()` 실패, 기동 후 2초 이내 종료, 포트 검증 실패로 정의한다.
12. backend가 정상 기동으로 판정되면 재시도 카운트가 초기화된다.
13. 재기동 루프는 메인 스레드/런루프를 block 하지 않는다.
14. 종료 원인/exit code와 재시도 카운트가 로그로 남는다.
15. 재기동은 단일 인스턴스로 동작하며 중복 start가 발생하지 않는다.

## Dev Notes
- `ProcessRunner`가 `Process`를 실행하므로 `terminationHandler`를 활용해 종료 감지를 추가할 수 있다.
  - `Process.terminationHandler`는 프로세스 종료 시점에 호출되는 콜백이며, `terminationReason`(정상/비정상)과 `terminationStatus`(exit code)를 수집해 재기동 판단/로그에 사용한다.
- 현재 구조상 `HelperLifecycle`는 signal 종료 처리만 담당하고, `ProcessRunner`가 실행/종료 제어를 단일 책임으로 가진다. 재기동 루프를 도입할 경우 `HelperLifecycle`에 루프를 추가하거나 별도 코디네이터를 둔다.
- endpoint 전달은 Story 117.8이 담당하며, fallback 탐지는 사용하지 않는다.
- 재기동 성공 시 endpoint 재전달이 필요하다면 `ProcessRunner`의 알림 전송 흐름을 재사용한다.
- 종료 감지는 `ProcessRunner`의 `terminationHandler` 기준으로 처리한다.
- `terminationHandler`에서 `terminationReason`/`terminationStatus`를 수집해 로그에 포함한다.
- Helper 종료 시 backend는 `terminate()` 기반 정상 종료를 보장한다.
- 강제 종료(SIGKILL) 등 OS가 종료 훅을 호출하지 않는 경우는 보장 범위 밖임을 문서에 명시한다.
- 의도적 종료 플래그를 두고 해당 경로에서는 종료 이벤트를 재기동으로 처리하지 않는다.
- 정상 기동 판정은 포트 LISTEN 검증 성공 + 2초 이상 유지로 정의하고, 성공 시 재시도 카운트를 리셋한다.
- `ProcessRunner`는 이미 actor 내부에 `isStarting` 가드가 있어 중복 start를 방지한다.
- 변경 대상: `apps/macos/Voyager/VoyagerHelper/Infrastructure/ProcessRunner.swift`, `apps/macos/Voyager/VoyagerHelper/Infrastructure/HelperLifecycle.swift`
- 의존성: `docs/voy-117/stories/117.9.helper-async-processrunner.md` 선행 필요.
- 참고: `docs/voy-117/epic.md#epic-goal`

### Testing
#### 수동 QA 절차
- 준비
  1. `.env`에서 `BACKEND_MODE`를 `source` 또는 `bundled`로 설정하고 앱/Helper를 실행한다.
  2. 로그에서 `PUBLIC_BACKEND_PROCESS_NAME` 값을 확인한다.
  3. backend PID를 확인한다. (`pgrep -f "$PUBLIC_BACKEND_PROCESS_NAME"` 또는 `lsof -iTCP:<port> -sTCP:LISTEN`)
  4. 동일 시나리오를 source/bundled 모드 각각 수행한다.
- 시나리오 A: 비정상 종료 재기동
  1. backend를 `kill -9 <PID>`로 강제 종료한다.
  2. 로그에 종료 원인/exit code와 `Retrying backend start in 1s (attempt 1/5)`가 출력되는지 확인한다.
  3. 재기동된 backend PID가 기존과 다른지 확인한다.
- 시나리오 B: 2초 이내 종료 시 backoff 증가
  1. backend가 뜬 직후 2초 이내에 `kill -TERM <PID>` 또는 `kill -9 <PID>`로 종료한다.
  2. 재시도 로그의 attempt가 증가하고 지연이 1→2→4→8→16s로 증가하는지 확인한다.
  3. 5회 초과 시 `Max restart attempts exceeded (5). Exiting helper.` 로그 후 Helper가 종료되는지 확인한다.
- 시나리오 C: 정상 기동 후 재시도 카운트 리셋
  1. backend를 2초 이상 유지한 뒤 `kill -9 <PID>`로 종료한다.
  2. 이후 재시도 로그가 `attempt 1/5`로 리셋되는지 확인한다.
- 시나리오 D: 의도적 종료에서는 재기동 없음
  1. 앱을 정상 종료하거나 Helper에 `kill -TERM <helperPID>`를 보낸다.
  2. backend 프로세스가 종료되는지 확인한다.
  3. 재기동 로그가 추가로 출력되지 않는지 확인한다.
- 시나리오 E: 시작 실패도 재시도 반영(선택)
  1. `.env`의 `PUBLIC_BACKEND_PROCESS_NAME`를 존재하지 않는 값으로 임시 변경한다.
  2. Helper 실행 시 `Failed to start backend`/`Failed to create process config` 로그와 backoff 재시도가 발생하는지 확인한다.
  3. 테스트 후 값을 원복한다.
- 공통 확인
  1. 재기동 루프 중에도 UI/메인 스레드가 응답성을 유지하는지 확인한다.
  2. 종료 원인/exit code/재시도 카운트 로그가 남는지 확인한다.
  3. 동시에 backend가 1개만 실행되는지 확인한다. (`pgrep -f "$PUBLIC_BACKEND_PROCESS_NAME"` 결과 1개)
