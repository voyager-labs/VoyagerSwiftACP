# Story 1.3: Beta Access Step (Server Verification)

## Status

Draft

## Story

**As a** 베타 사용자,  
**I want** `Beta Access` 단계에서 서버 검증을 통해 베타 활성 상태를 확인하고,  
**so that** 베타 접근이 확인되기 전에는 다음 단계로 진행하지 않게 하여 품질/정책을 준수할 수 있다.

## Acceptance Criteria

1. `Beta Access` 스텝은 서버 검증으로 `Active` / `Not Active` / `Check failed` 상태를 표시한다.  
2. `Active`가 되기 전까지 `Next`는 비활성화된다(블로킹 유지).  
3. 네트워크/서버 오류로 `Check failed`가 되면 `Retry`로 재시도할 수 있다.  
4. 실패 상태에서도 사용자에게 가이드(원인/다음 행동)가 표시되어 재시도 루프에서 이탈하지 않는다.  
5. `Active`가 되면 상단 요약 뱃지(`Beta`)가 `Granted` 상태로 갱신된다.  

## Tasks / Subtasks

- [ ] Define beta access verification contract (AC: 1–5)
  - [ ] Decide which server is authoritative (backend? remote?) and define endpoint + response schema
  - [ ] Define error mapping: timeout/offline/5xx → `Check failed`
- [ ] Implement `BetaAccessFeature` (TCA) + dependency injection (AC: 1–5)
  - [ ] Add a `BetaAccessClient` TCA dependency (live + test), similar to existing dependency patterns
  - [ ] Implement `BetaAccessFeature` reducer handling:
    - [ ] `onAppear` → trigger verification
    - [ ] `retryTapped` → trigger verification (cancel in-flight if needed)
    - [ ] `verificationResponse` → set status (`Active` / `Not Active` / `Check failed`)
- [ ] Implement Beta Access step UI (SwiftUI + TCA) (AC: 1–4)
  - [ ] Render status: `Active` / `Not Active` / `Check failed`
  - [ ] Provide `Retry` and guidance copy in `Check failed` (and optionally `Not Active`)
  - [ ] Ensure `Next` remains disabled until `Active` (gating owned by `OnboardingFeature`)
- [ ] Integrate with Onboarding root gating + header badges (AC: 2, 5)
  - [ ] `OnboardingFeature` uses `BetaAccessFeature.State` to decide `Next` availability
  - [ ] `OnboardingShell` header badge for `Beta` reflects `Active` → `Granted`
- [ ] Tests (AC: 1–5)
  - [ ] Unit tests for state transitions using `TestStore` with stubbed `BetaAccessClient` responses

## Dev Notes

- Depends on: Story 1.2 (step state machine exists)
- UX/AC source:
  - `docs/frontend/onboarding-window-spec.md#beta-access`
  - `docs/frontend/onboarding-window-spec.md#acceptance-criteria-locked-for-voy-111`
- TCA architecture notes:
  - This story should be implemented as the `BetaAccessFeature` child reducer scoped from the root `OnboardingFeature` (created in Story 1.2).
  - `OnboardingFeature` owns cross-step rules (`Next` gating, progress header, status badges). `BetaAccessFeature` owns verification mechanics and its local status UI.
- **BLOCKER / Required Input:** “서버 검증”의 대상 서버/엔드포인트/응답 스키마가 현재 문서에 정의되어 있지 않다.
  - This story should not be started until the contract is explicitly defined.

### Testing

- Unit tests should simulate:
  - Active → Next enabled
  - Not Active → Next disabled
  - Check failed + Retry loop
