## Profile

  - 독일 베를린주 베를린 거주
  - 직접 제품을 만들고 시장 반응을 빠르게 확인하는 초기 테크 스타트업 파운더
- 성향
  - 출시 준비, 메시징, 고객 반응 확보를 직접 끌고 가는 창업자
  - 같은 제품 자산을 출시 시점과 채널에 맞게 반복 재포장하며, "이번 릴리즈를 외부에 어떻게 보여줄 것인가"를 계속 조정하는 성향
- 역할
  - 기능 출시가 정해지면 스크린샷, 데모 영상, 릴리즈 노트, 온보딩 카피, 외부 공유 세트를 한 묶음으로 만들어 시장에 내보내는 역할
  - 투자자 업데이트도 직접 챙기지만, 중심은 어디까지나 출시 자산을 최신 상태로 묶고 채널별로 다시 꺼내 쓰는 데 있음
- 업무 밀도
  - 배포 당일에는 캡처, 녹화, 카피 수정, 공유 링크 정리, 채널별 패키지 준비가 한꺼번에 몰림
  - 같은 기능이라도 고객 온보딩용, Product Hunt용, 뉴스레터용, 소셜용으로 각각 다른 묶음이 필요해 출시 단위 파일 집합이 빠르게 누적됨
- 사용 도구
  - 개발: GitHub, Cursor, Vercel
  - 제품/디자인: Figma, Framer, Screen Studio
  - 문서/커뮤니케이션: Notion, Google Docs, Slack, Email
  - 채널 운영: X, Product Hunt, 뉴스레터 툴
- 도입 계기
  - 새 기능을 배포할 때마다 스크린샷, 데모, 릴리즈 노트, 온보딩 카피, 외부 공유 세트를 흩어진 위치에서 다시 한 벌씩 모아야 함. 매 출시마다 거의 같은 출시 팩을 새로 조립하는 순간 Voyager 필요성이 커짐

## Context

1. ### 출시 당일에 대외 노출용 자산을 한 번에 포장해야 함

- 핵심 상황
  - 기능 배포가 결정되면 스크린샷, 데모 영상, 릴리즈 노트, 온보딩 문구, 외부 공유 세트가 같은 날 안에 완성돼야 함
  - 이 자산들은 로컬 폴더, Figma, Notion, Screen Studio, 메일 초안 등 여러 위치에 흩어져 있어 매번 다시 모으는 작업이 반복됨
- 현재 방식
  - 최근 수정한 파일을 기준으로 여기저기서 자료를 찾아 한 세트처럼 묶음
  - 채널별로 필요한 포장이 다르면 최신본을 다시 확인하고 복사본을 만듦
  - 이전 출시에서 잘 썼던 구성이 있어도, 이번 버전에 맞는지 처음부터 다시 확인해야 함

2. ### 같은 출시 자산을 대상과 채널에 맞게 계속 다시 꺼내 써야 함

- 핵심 상황
  - 같은 기능 업데이트라도 고객 온보딩 설명, Product Hunt용 문구, 뉴스레터 하이라이트, 소셜 공유용 요약이 각각 따로 필요함
  - 투자자 진행 공유도 같은 자산에서 출발하지만, 어디까지나 출시 결과를 요약하는 보조 맥락에 가까움
- 현재 방식
  - 기능 관련 문서와 화면 캡처를 다시 찾고, 채널에 맞는 버전으로 조합하며 메시지를 손봄
  - 무엇이 가장 최신인지 기억에 의존하다 보니 다시 확인하는 시간이 큼
  - 채널이 추가되거나 이전 출시를 다시 꺼내야 할 때는 사실상 다시 조립해야 함

## Pains

1. ### 출시 단위로 필요한 자산 번들을 다시 모으는 일이 매번 반복된다

- 기능 릴리즈 자체보다 스크린샷, 데모, 릴리즈 노트, 온보딩 카피, 외부 공유 세트를 다시 한 벌 모으는 데 시간이 많이 듦
- 채널이 바뀔 때마다 필요한 포장 단위가 달라져 작업이 자주 끊기고, 출시 속도보다 파일 재조립 속도가 병목이 됨
- 이전 출시에서 만든 팩이 있어도 이번 버전에 맞는 최신 조합인지 재확인해야 해서 재사용 이점이 사라짐

2. ### 채널별 재포장마다 최신 파일 기준이 흔들리고 중복이 늘어난다

- 어떤 캡처와 카피가 이번 출시의 기준인지 확신하기 어려워 비슷한 파일을 반복 생성하게 됨
- 저장된 자료 묶음이 있어도 최신 버전 반영이 안 됐을까 봐 결국 수동으로 다시 확인함
- 채널이 늘어날수록 같은 자산의 변형이 여기저기 흩어져, "한 번 만들고 다시 쓴다"가 아니라 "매번 새로 조립한다"에 가까워짐

## Goals

1. 특정 출시 맥락을 열면 스크린샷, 데모, 릴리즈 노트, 온보딩 카피, 외부 공유 세트가 최신 기준으로 한 번에 모여 있는 상태
2. 대상과 채널이 달라도 같은 출시 자산 세트에서 바로 재포장할 수 있고, 처음부터 다시 모으지 않아도 되는 상태
3. 이전 출시의 자산 구성과 포장 방식이 다음 출시에서도 그대로 다시 꺼내 쓸 수 있는 상태

### JTBD03. 잘 작동한 출시 패턴을 다음 릴리즈에서 다시 불러와 재사용하기

- 이전 출시에서 효과적이었던 자산 구성과 채널별 포장 순서를 다음 릴리즈에서도 같은 흐름으로 반복하고 싶다.
- 출시가 거듭될수록 어떤 파일 조합과 포장 절차가 잘 작동했는지가 누적되지만, 현재는 그 패턴을 다음 출시에 그대로 불러올 방법이 없어 매번 새로 결정해야 한다.
- 저장된 출시 세트와 포장 흐름을 그대로 다시 열어, 최신 자산만 갈아끼우면 바로 다음 출시를 시작할 수 있는 반복 가능한 워크플로가 돼야 한다.
