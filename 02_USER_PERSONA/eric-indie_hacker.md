## **Context**

1. ### **여러 인디 제품의 아이디어∙스펙∙실험 기록 누적**

* 핵심 상황  
  * 여러 개의 웹∙iOS∙macOS 사이드 프로젝트를 병행하며, 각 제품마다 아이디어 노트·간단한 스펙·실험 기록이 따로 쌓임  
  * 이런 기록은 Obsidian 노트, GitHub Issues, 마크다운 파일, 링크·스크린샷 등 여러 형식으로 흩어져 있음  
* 현재 방식  
  * 새 기능이나 실험을 준비할 때, 예전에 비슷한 걸 했는지 떠올리며 제목·키워드로 노트/이슈를 검색하고 후보를 하나씩 열어봄  
  * 에서 무엇을 바꾸고 어떤 결과였는지”처럼 질문 단위로 자료를 모으고 싶어도, 제품·날짜·주제가 섞여 있어 여러 위치를 오가며 손으로 조합함

2. ### **런칭∙프로모션용 마케팅∙지표 자료 누적**

* 핵심 상황  
  * 작은 기능 추가, 가격·온보딩 실험, 소규모 런칭을 자주 돌리며, 그때마다 스크린샷·녹화본·릴리즈 노트·소셜/뉴스레터 카피 초안이 짧은 기간에 몰려 나옴  
  * 같은 실험이라도 Product Hunt, Reddit, Indie Hackers, X, 앱스토어 등 채널별로 카피·CTA·이미지를 조금씩 다르게 제작  
* 현재 방식  
  * 채널명·날짜를 파일명이나 폴더명에 붙여 구분하지만, 실험이 몇 번 쌓이면 규칙과 예외가 섞여 금방 흐려짐  
  * 실험 결과를 다시 볼 때 Desktop·Downloads·프로젝트 폴더·Figma·Stripe·애널리틱스 대시보드를 오가며 “당시 게시본”과 매출·트래픽·리텐션 숫자를 손으로 맞춰봄

3. ### **파일 정리 규칙 부재로 인한 임시 저장∙리셋 패턴**

* 핵심 상황  
  * 프로젝트 시작 때 잡아둔 폴더 구조·파일 이름 규칙은 몇 주만 지나도 예외가 쌓이면서 흐려짐  
  * 런칭∙큰 업데이트 직전에는 캡처·영상·슬라이드·마케팅 이미지가 Desktop·Downloads에 단기간에 폭발적으로 쌓이고, 출시 전까지는 거의 손대지 않음  
* 현재 방식  
  * 여유가 생기면 일부만 프로젝트 폴더로 옮기거나 \`old\`, \`archive\`, \`tmp\` 같은 임시 폴더에 던져 넣고, 나머지는 그대로 방치  
  * 파일 수가 심리적 임계치를 넘었다고 느끼면 세부 분류를 포기하고 대량 삭제·리셋을 택하고, 이후 필요한 자료는 각 플랫폼에서 다시 내려받거나 처음부터 새로 만듦

## **Pains**

1. ### **과거 실험·기능 히스토리를 한 번에 복원하기 어려움**

* 예전에 했던 실험/기능이 떠올라도, 관련 노트·이슈·스크린샷·지표가 여러 곳에 흩어져 있어 다시 모으는 데 시간이 많이 듦  
* 결국 “그때 대충 이렇게 했던 것 같다”는 기억만으로 새 실험을 설계하거나, 비슷한 조사·정리를 처음부터 다시 하게 됨

2. ### **채널·버전 파편화로 동작하는 마케팅 자산을 재사용 난도 증가**

* Product Hunt, Reddit, Indie Hackers, X, 앱스토어 등에 올렸던 카피·이미지·썸네일이 채널·날짜별로 제각각 저장되어 있음  
* 어떤 조합이 잘 먹혔는지 확인하고 다시 쓰는 것보다, 매번 새 카피·이미지를 만드는 쪽이 더 빠르게 느껴짐

3. ### **실험/런칭 단위로 자산과 지표가 묶여 있지 않아, 결정 근거를 설명하기 힘듦**

* 화면 변경은 스크린샷/녹화, 숫자는 대시보드·CSV, 요약은 노트에 따로 남아 있어 “이 결과가 어떤 변경 때문인지”를 나중에 한 번에 보기 어려움  
* 가격·온보딩·플로우를 바꿀 때도, 과거 어떤 판단이 어떤 자료를 근거로 나온 것인지 다시 설명하기가 부담스러움

4. ### **임시 정리·리셋 위주 파일 관리로 히스토리가 끊기고, 정리/구조 변경에 부담**

* Desktop·Downloads·임시 폴더에 파일이 쌓이다가 어느 순간 대량 삭제·일괄 이동으로 정리해 버려, 중간 과정이 통째로 사라지는 구간이 생김  
* 폴더 구조 변경이나 이름 일괄 수정 같은 작업은 “실수 나면 복구 못 할 것 같다”는 느낌 때문에 미루게 되고, 결국 쌓아두다 한 번에 비우는 패턴을 반복하게 됨

## **Goals**

1. 예전에 했던 실험·기능·런칭을 다시 열었을 때, 자료 찾느라 헤매지 않고 바로 이어서 손댈 수 있는 상태  
2. 여러 채널에 뿌렸던 카피·이미지 중 잘 먹힌 것들만 따로 모여 있어, 다른 프로젝트나 다음 런칭에 쉽게 다시 써먹을 수 있는 상태  
3. 동시에 돌리는 앱·웹들 중 어디를 밀고 무엇을 잠깐 접어둘지, 간단한 기록과 숫자만 보고도 금방 판단할 수 있는 상태  
4. 파일이 쌓여도 하드 리셋까지 가지 않고, 구조를 조금씩 손보면서 히스토리를 유지한 채 정리해 나갈 수 있는 상태

* 특정 실험/런칭 이름을 떠올리면, 관련 커밋·릴리즈 노트·스크린샷·지표 스냅샷이 “한 세트”로 묶여서 바로 열리길 싶다.

* 잘 된 실험은 그대로 복제해서 다른 제품이나 다음 버전의 실험 템플릿으로 쓰고, 일부 설정만 바꿔 재사용하고 싶다.  
* 중단했던 실험·기능·런칭을 다시 살릴 때도, 이 세트를 불러와 “이어서 작업”하는 느낌으로 바로 손대고 싶다.  
* 시스템은 실험/기능/런칭 같은 작업 단위를 정의하고, 관련 파일·링크·지표를 하나의 작업 세트로 묶어 저장·불러오기·복제할 수 있도록 지원해야 한다.  
* 작업 세트 간 유사도를 바탕으로, 새 실험을 설계할 때 참고하거나 복제할 만한 과거 세트를 추천해주는 기능을 제공해야 한다.

### **JTBD03. 포트폴리오에서 집중·보류·정리할 제품 선별하기**

* 동시에 돌리는 여러 앱·웹에 대해, 최근 몇 주 동안 어떤 작업을 했고 유저·매출 반응이 어떠했는지 한 화면에서 보고 싶다.  
* “이번 주에는 이 서비스 밀고, 이 두 개는 홀드, 이건 정리” 같은 결정을 감이나 기분이 아니라 작업 기록과 숫자를 기준으로 내리고 싶다.  
* 잠깐 접어둔 프로젝트를 다시 볼 때, 왜 멈췄고 그 시점까지 무엇을 만들었는지, 과거 실험·런칭 히스토리와 함께 빠르게 복기하고 싶다.  
* 어느 제품에 시간을 더 쓰는 게 장기적으로 유리할지, 각 서비스의 작업·실험·지표 흐름을 나란히 놓고 비교해보고 싶다.  
* 나중에 “왜 이때 이 서비스를 접었는지/밀었는지”를 스스로 다시 설명해야 할 때, 그 시점의 히스토리와 근거를 쉽게 찾아보고 싶다.  
* 시스템은 제품별로 작업 히스토리·실험 결과·핵심 지표를 묶어서 보여주고, 밀기/홀드/정리 같은 상태 결정을 기록할 수 있는 포트폴리오 뷰를 제공해야 한다.  
* 포트폴리오 뷰에서 이런 결정과 근거를 함께 남기고, 나중에 시간 범위를 바꿔 보며 판단의 일관성과 변화를 추적할 수 있게 지원해야 한다.

### **JTBD04. 히스토리를 남기면서 안전하게 정리·아카이브하기**

* Desktop·Downloads·프로젝트 폴더에 쌓인 파일들 중 무엇을 지우고, 무엇을 옮기고, 무엇을 그대로 둘지 한 번에 훑어보고 싶다.  
* “지금은 안 쓰지만 나중에 필요할 수도 있는 파일”과 “두 번 다시 안 볼 파일”을 구분해서, 리셋이 아니라 점진적인 정리를 하고 싶다.  
* 폴더 구조를 손보거나 이름을 일괄 변경해도, 나중에 문제가 생기면 이전 상태로 되돌릴 수 있다는 느낌이 있길 싶다.  
* 실험/런칭 히스토리가 끊기지 않도록, 아카이브로 보낸 파일도 최소한의 단서와 함께 남겨 두고 싶다.    
* 정리 작업을 하기 전에 “이번에 어떤 파일들이 어떻게 바뀌는지”를 요약으로 보고, 일부만 먼저 적용해보는 식으로 시험 운행을 해보고 싶다.  
* 시스템은 마지막 사용 시점·유사도·중복 여부 등을 기준으로 정리 후보를 제안하고, 사용자가 유지/이동/삭제/아카이브 액션을 묶어서 적용할 수 있도록 해야 한다.  
* 구조 변경·대량 이동·삭제 같은 작업에 대해 영향 범위 미리보기, 부분 적용, 되돌리기 기능을 제공해, 히스토리를 유지한 채 안전하게 정리를 반복할 수 있게 해야 한다.
