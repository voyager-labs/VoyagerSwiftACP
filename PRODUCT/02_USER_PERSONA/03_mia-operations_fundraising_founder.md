# Mia, 운영·투자 커뮤니케이션형 파운더

[사용자 페르소나](00_index.md)

## Profile

- 거주지
  - 미국 캘리포니아주 샌프란시스코 베이 에어리어 거주
  - 제품 출시 이후 운영 루프와 투자자·파트너 업데이트를 반복적으로 챙기는 초기 테크 스타트업 파운더
- 성향
  - 릴리즈 후속 대응, 고객 응답 패키징, 파트너·투자자 업데이트 준비, 주간 운영 리뷰를 주도하는 창업자
  - 반복되는 운영 산출물을 매번 최신 파일 기준으로 다시 구성해야 하는 구조적 부담을 크게 느끼는 성향
- 역할
  - 기능이 배포된 뒤 고객 대응 자료, 내부 운영 정리, 파트너 공유 팩, 투자자 업데이트 자료를 같은 주기 안에서 이어서 만드는 역할
  - 같은 릴리즈 맥락의 파일이라도 내부용과 외부용을 따로 검토하며 다시 써야 하는 운영 책임을 짐
- 업무 밀도
  - 릴리즈 직후에는 고객 문의 답변, QA 정리, 운영 메모, 스크린샷, 내부 회고, 투자자 진행 보고가 한꺼번에 쌓임
  - 같은 파일이라도 내부 회고용, 고객 안내용, 파트너 공유용, 투자자 업데이트용으로 서로 다른 팩을 만들어야 해서 반복 작업이 누적됨
- 사용 도구
  - 개발/운영: GitHub, Linear, Cursor, Terminal
  - 문서/정리: Notion, Google Drive, Slack, Email
  - 자료 제작: Figma, Keynote, Screen Studio
  - 운영 루틴: Shortcuts, Zapier, 스크립트 기반 자동화

## Context

1. ### 릴리즈 이후 운영용 자료가 계속 다시 필요해진다

- 핵심 상황
  - 기능을 배포하고 나면 고객 문의 답변, QA 메모, 수정 스크린샷, 운영 메모, 공유 자료가 빠르게 쌓임
  - 같은 주 안에서도 고객 대응용, 내부 리뷰용, 투자자 공유용으로 서로 다른 업데이트 팩이 계속 필요해짐
- 현재 방식
  - 급한 요청부터 처리하느라 파일 분류와 팩 구성을 뒤로 미루고, 필요할 때마다 최근 파일과 관련 메모를 다시 모음
  - 릴리즈가 하나 끝날 때마다 비슷한 정리 작업을 또 처음부터 시작하게 됨

2. ### 내부용과 외부용 자료를 나누는 순간 수동 검수가 늘어난다

- 핵심 상황
  - 같은 릴리즈 맥락의 파일이라도 내부 회고, 고객 안내, 투자자 공유용으로 각각 다른 포함 기준과 노출 수준이 필요함
  - 실수 한 번이면 잘못된 자료를 외부에 공유할 수 있다는 부담이 큼
- 현재 방식
  - 어떤 파일을 어디까지 공유해도 되는지 매번 다시 선별하고, 마지막 순간에 한 번 더 검수함
  - 반복 루틴이 있어도 파일 기준이 흔들리면 결국 다시 손으로 맞추게 됨

## Pains

1. ### 릴리즈 이후 반복되는 운영·업데이트 팩을 계속 처음부터 다시 만든다

- 고객 대응, 내부 정리, 투자자 공유가 겹칠수록 필요한 파일을 다시 찾는 시간이 늘어남
- 이전에 만들어 둔 구성과 기준이 다음 주기에 그대로 이어지지 않아, 업데이트 팩을 매번 다시 조립하게 됨
- 결과적으로 운영 리듬보다 파일 재구성 비용이 더 크게 느껴지는 순간이 많다

2. ### 대상별로 자료를 나누는 과정이 안정적으로 반복되지 않는다

- 내부용과 외부용이 섞이지 않게 준비하려면 같은 자료 묶음을 여러 번 다시 확인해야 함
- 마지막 순간 수동 검수가 반복되면서, “한 번 정한 기준을 다음에도 그대로 쓴다”는 감각이 약함
- 안전하게 나누는 일 자체가 별도의 추가 작업처럼 느껴진다

## Goals

1. 릴리즈 이후 반복되는 운영·업데이트 팩을 최신 파일 기준으로 빠르게 다시 만들 수 있는 상태
2. 내부용과 외부용 자료 세트를 섞지 않고 안정적으로 나눠 준비할 수 있는 상태
3. 주간 운영·투자자 커뮤니케이션 루틴을 매번 처음부터 다시 조립하지 않아도 되는 상태
