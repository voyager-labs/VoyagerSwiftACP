# FEATURE_SPECS 작성 규칙

`PRODUCT/05_FEATURE_SPECS/` 문서는 Voyager의 **interaction 단위 기능 스펙**을 정리하는 문서입니다.
이 문서는 개별 스펙이 단순 QA 체크리스트에 머무르지 않고, **기능 의도 / 상태 변화 / 사용자 피드백 /
관측 포인트 / 인접 인터랙션 연결**까지 일관되게 담도록 하기 위한 규칙을 정의합니다.

## 문서 목표

FEATURE_SPEC는 아래 질문에 답할 수 있어야 합니다.

- 이 인터랙션은 **왜** 존재하는가?
- 사용자는 **어디서 / 어떻게** 이 인터랙션에 진입하는가?
- 실행되면 **무슨 결과가 성립**해야 하는가?
- 그 과정에서 **어떤 상태가 바뀌는가?**
- 사용자는 **어떤 피드백**을 받는가?
- 예외나 실패 상황에서 **시스템이 어떻게 반응**해야 하는가?
- 이 인터랙션은 **무엇에 의존**하는가?
- 이 행동을 **무엇으로 관측**할 것인가?
- 이 문서와 **함께 읽어야 할 인접 인터랙션**은 무엇인가?

## 핵심 원칙

- **interaction 단위로 쓴다.**
    - 하나의 문서는 하나의 `interaction_id`를 기준으로 작성한다.
- **고정 섹션 셸을 유지한다.**
    - 문서마다 섹션을 빼고 넣는 방식보다, 동일한 섹션 구조를 유지하고 내용 밀도를 조절한다.
- **비어 있는 섹션도 남긴다.**
    - 해당 없음은 `-`
    - 아직 미정은 `TBD`
- **`NULL`은 사용하지 않는다.**
    - 이 레포의 기본 결측 표기는 `-` 또는 `TBD`다.
- **기획 의도 / 결과 / 상태 변화를 구분한다.**
    - `Intent`는 왜 필요한지,
    - `Expected Outcome`은 어떤 결과가 성립해야 하는지,
    - `State Changes`는 어떤 상태가 어떻게 바뀌는지 적는다.
- **과도한 PRD화는 피한다.**
    - 구현 상세, 내부 아키텍처, 코드 구조, 데이터 모델 설계까지 내려가지 않는다.
- **관찰 가능한 결과를 우선한다.**
    - 사용자에게 보이는 상태, 시스템의 확인 가능한 반응, 추적 가능한 이벤트를 중심으로 적는다.

## 표준 섹션 구조

모든 FEATURE_SPEC는 아래 섹션을 기본으로 포함합니다.

1. `Metadata`
2. `Intent`
3. `Trigger / Entry Points`
4. `Preconditions`
5. `Expected Outcome`
6. `State Changes`
7. `User-visible Feedback`
8. `Edge Cases / Failure Handling`
9. `Acceptance Criteria`
10. `Permissions / Dependencies`
11. `Observability / Analytics`
12. `Related Interactions`
13. `Source`

필요할 때만 아래 보조 섹션을 추가할 수 있습니다.

- `Boundary Notes`

## 결측값 규칙

### 해당 없음

해당 섹션이 현재 인터랙션에 적용되지 않으면 `-`를 사용합니다.

예:

```md
## Permissions / Dependencies

-
```

### 아직 미정

필요한 항목이지만 아직 결정되지 않았다면 `TBD`를 사용합니다.

예:

```md
## Observability / Analytics

- TBD
```

## 섹션별 작성 기준

### 1. Metadata

문서의 식별 정보와 인벤토리 연결 정보를 적습니다. 기존 메타데이터 필드는 가능한 한 유지합니다.

기본 예시:

- Interaction ID
- Interaction Type
- Feature
- Category Key
- Feature ID
- Status
- Summary
- Related Region
- Menu
- Shortcut

### 2. Intent

사용자가 이 인터랙션을 쓰는 **핵심 이유**를 한두 줄로 적습니다.

좋은 예:

- 사용자가 여러 Entry의 이름을 반복 수작업 없이 한 번에 정리하려고 한다.
- 사용자가 권한 부여 절차 중 길을 잃지 않고 현재 상태를 확인하려고 한다.

피할 것:

- 구현 방식 설명
- AC 문장 반복

### 3. Trigger / Entry Points

사용자가 이 기능에 진입하는 경로를 적습니다.

예:

- 메뉴에서 진입
- 컨텍스트 메뉴에서 진입
- 단축키로 호출
- Command Palette에서 호출
- 특정 선택 상태에서만 노출
- 다른 기능 흐름 중 후속 단계로 진입

### 4. Preconditions

기능이 정상적으로 호출되기 전에 만족되어야 하는 조건을 적습니다.

예:

- 하나 이상의 Entry가 선택된 상태
- 설정 창의 General 탭이 열려 있는 상태
- 현재 페이지가 디렉토리 모드인 상태

### 5. Expected Outcome

인터랙션이 끝난 뒤 **사용자 관점에서 성립해야 하는 결과**를 적습니다.

예:

- 사용자가 이전에 보던 페이지로 돌아간다.
- 선택된 Entry 이름이 일괄 변경된 상태를 확인할 수 있다.
- 권한 상태를 바탕으로 다음 행동을 판단할 수 있다.

### 6. State Changes

이 인터랙션으로 인해 **어떤 상태가 어떻게 바뀌는지**를 적습니다.

`Expected Outcome`과의 차이:

- `Expected Outcome` = 무엇이 성립해야 하는가
- `State Changes` = 무엇이 갱신 / 이동 / 유지 / 초기화되는가

예:

- current page가 이전 history entry로 바뀐다.
- history pointer가 한 단계 뒤로 이동한다.
- 선택된 Entry들의 이름 값이 새 이름으로 갱신된다.
- 권한 상태 배지가 `미허용`에서 `허용됨`으로 바뀐다.

### 7. User-visible Feedback

실행 전 / 중 / 후 사용자가 보게 되는 피드백을 적습니다.

예:

- 미리보기
- 진행 중 표시
- 완료 안내
- 실패 안내
- 재시도 안내
- 경고 메시지

### 8. Edge Cases / Failure Handling

특수 상황과 그에 대한 시스템 반응을 함께 적습니다.

구성 원칙:

- 어떤 예외가 존재하는가
- 그 예외를 시스템이 어떻게 처리하는가

예:

- 이름 충돌이 발생하면 적용 전 경고를 표시한다.
- 일부 항목만 실패하면 성공 / 실패 항목을 분리해 보여준다.
- 상태 반영이 지연되면 재확인 필요 상태를 안내한다.

### 9. Acceptance Criteria

검증 가능한 결과를 Given / When / Then 구조의 한국어 문장으로 적습니다.

#### AC 문장 형식

- 작성 형식: `...한 상황에서, ...하면, ...해야 한다.`
- 권장 매핑:
    - Given: `...한 상황에서`
    - When: `...하면`
    - Then: `...해야 한다`

#### AC 작성 예시

- `두 개 이상의 Entry가 선택된 상황에서, 배치 이름 변경을 적용하면, 규칙에 따라 이름이 일괄 변경되어야 한다.`
- `페이지 히스토리에 이전 항목이 있는 상황에서, 뒤로 가기를 호출하면, 현재 탭이 이전 페이지로 전환되어야 한다.`

#### 작성 노트

- AC 한 줄은 하나의 검증 가능한 결과만 다룹니다.
- 주어를 명확히 적습니다. 예: 사용자, 시스템
- 기대 결과는 관찰 가능하게 적습니다. 예: 표시된다, 저장된다, 전환된다, 실행된다

### 10. Permissions / Dependencies

기능이 성립하기 위해 필요한 **외부 조건 / 시스템 조건**을 적습니다. 이 섹션은 구현 상세가 아니라,
기능 계약에 가까운 의존성만 적습니다.

예:

- Full Disk Access 권한 상태 조회 가능해야 함
- 네트워크 연결 필요
- 인덱스가 준비된 상태여야 함
- 특정 OS 정책에 따라 직접 이동이 제한될 수 있음

적용되지 않으면 `-`를 사용합니다.

### 11. Observability / Analytics

이 인터랙션을 제품적으로 어떻게 관측할지 적습니다. 세부 이벤트 설계가 아니어도, 최소한의 관측
포인트는 남깁니다.

예:

- 인터랙션 진입
- 적용 시도
- 성공
- 취소
- 부분 실패
- 재시도

아직 미정이면 `TBD`, 정말 해당 없음이면 `-`를 사용합니다.

### 12. Related Interactions

함께 읽어야 하는 인접 인터랙션을 연결합니다. 문서가 고립되지 않도록 가능한 한 채웁니다.

예:

- `EAC-004-rename_entry.md`
- `EAC-003-undo_entry_action.md`
- `SET-002-verify_system_permission_status.md`

연결할 항목이 아직 정리되지 않았다면 `TBD`를 사용합니다.

### 13. Source

이 문서가 어떤 인벤토리 / 라인 / 기준 문서를 바탕으로 작성되었는지 적습니다.

예:

- Inventory 파일
- Source line
- Writing guide
- Template

## 보조 섹션

### Boundary Notes

이 문서의 경계가 특히 흔들리기 쉬운 경우에만 추가합니다. 모든 문서에 강제하지 않습니다.

예:

- 이번 문서는 배치 이름 변경의 규칙 적용 흐름만 다룬다.
- 정규식 기반 고급 변환이나 외부 스크립트 실행은 다루지 않는다.

## 적용 원칙

- 기존 문서를 한 번에 모두 마이그레이션하지 않습니다.
- 새 문서 또는 크게 다시 쓰는 문서부터 우선 적용합니다.
- 문서 밀도가 과도해지면 섹션을 제거하는 대신, `-` / `TBD`로 유지하고 내용 밀도만 줄입니다.
